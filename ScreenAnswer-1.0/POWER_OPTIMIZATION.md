## 비교 측정

1.0 공통 감지 경로를 실제 Windows UIA가 별도 테스트 창만 읽도록 고정해 측정했습니다. 외부 창이나 사용자의 문서 내용은 수집하지 않았습니다. 자동 선택 대기 50ms, 워밍업 1.5초, 측정 구간 약 8초, API 요청 0회입니다. 마지막 입력·활성 창 신호도 동일한 유휴 값으로 고정했습니다. 원 감지와 단축키의 대기 스레드를 함께 포함하며, 메인 UI와 실제 번역·네트워크 작업은 측정 대상에서 제외했습니다. 비교 기준 소스는 최적화 전 커밋 `8afd881`입니다.

| 항목 | 변경 전 | 변경 후 |
|---|---:|---:|
| UIA 원문 조회 | 79회 | 8회 |
| 프로세스 CPU 시간 | 1.5625초 | 0.125초 |
| 단일 코어 기준 평균 CPU | 19.515% | 1.56% |

이 표본에서 UIA 조회는 89.9%, CPU 시간은 92% 줄었습니다. 짧은 유휴 시험의 결과이며, PC 전체 배터리 소모량이나 실제 사용 시간 절감률을 뜻하지 않습니다. 실제 PDF·브라우저, 마우스 사용량과 다른 앱에 따라 결과가 달라집니다. 검사 당시 실행 중인 설치 앱은 확인되지 않아 기존 실제 사용 세션의 배터리 비중을 특정할 수 없었습니다.

## 유지한 동작과 반응 시간

- 선택 대기 설정 50ms, 화면·선택 번역, 원 동작·연속 클릭, 정상 답변 말풍선과 오류 말풍선 차단을 유지합니다.
- 드래그 중인 중간 텍스트는 보내지 않습니다. 버튼을 뗀 뒤와 실제 전송 직전에는 원문을 다시 확인합니다. 요청 중 새 선택과 같은 문구 재선택도 보존합니다.
- 완전히 유휴 상태에서 첫 UI 이벤트 처리는 최대 200ms 간격이므로, 기존 50ms 대비 최대 150ms의 추가 대기가 생길 수 있습니다. 입력 감지 후와 요청 중에는 빠른 주기를 사용합니다.
- 사용자 입력 없이 프로그램 자체가 선택 내용을 바꾼 경우에는 최대 약 1초의 재확인 간격이 적용됩니다. Windows 입력 상태 확인에 실패하면 빠른 원문 조회로 복귀합니다.
- 모델·프롬프트·해상도를 낮춰 정확도를 바꾸거나, 사용 중인 자동 선택·마우스 원 기능을 임의로 끄지 않았습니다. 기존 설정과 암호화된 API 키를 보존합니다.

## 추가 점검 결과

- 화면 캡처는 기존에 2560px 제한과 JPEG 인코딩, 이미지 자원 정리가 적용되어 있습니다.
- 응답 스트리밍은 기존 0.25초 묶음 표시를 유지합니다. 토큰마다 창 전체를 다시 그리지 않습니다.
- 재선택 의도를 보존하기 위해 API 결과 캐시나 새 자동 요청을 추가하지 않았습니다. 화면·원문·답변을 디스크에 저장하지 않습니다.
- 향후 검토 후보: UIA 선택 변경 이벤트 기반 감지, 마우스 기능이 모두 꺼졌을 때 네이티브 훅 해제. Edge PDF 이벤트 누락과 재활성화 동작 검증이 필요하므로 이번에는 안정적인 입력 감지를 우선했습니다.

## 재현

개발 의존성을 설치한 뒤 `python benchmark_power.py --seconds 8 --output build/power.json`으로 현재 코드를 측정할 수 있습니다. 별도 버전의 `src`를 비교하려면 `--source 경로`를 지정합니다. 측정 중 표시되는 창은 테스트 원문 전용이며 API 요청을 보내지 않습니다.
